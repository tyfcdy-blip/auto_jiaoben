# nine 报表与离线预检接入（M5.1）

本接入包只允许 `check`（报表）和 `preflight`（离线结构预检）。`upload`、未知操作和额外 `execute` 参数均拒绝。**没有正式上传能力，也没有读取原项目真实配置、凭据或业务 Excel。** 钉钉仍由工作台统一负责，本适配器不包含通知代码。

## 原程序复用方式

已只读阅读用户提供目录的 `AGENTS.md` 和两份 Python 源码。打包工具只读取明确的 `pdd_billing_check.py`、`pdd_billing_warehouse_load.py`，原字节复制到新包的 `legacy/`；只另加入口映射、离线启动器、参数定义和来源摘要。不复制 `warehouse.local.json`、店铺账号表、账单、输出或 Git 内容，不修改原程序业务规则。

```powershell
.\.venv\Scripts\python.exe integrations/nine/package.py --source 'C:\Users\JIE\Desktop\拼多多\nine' --output runtime/nine-adapter.zip
```

输出必须位于原项目之外且不能覆盖已有包。对其他来源使用显式 `--source`。用户源文件未提供可公开再分发许可，本包仅供当前授权的内部接入，不据此主张公开发布权。

两个旧脚本仍各自读取原始账单；报表输出不是上传程序输入。脚本通过原有命令行参数启动，不复制合并、金额、日期或筛选逻辑。

## 输入与参数

同一输入批次包含店铺映射表和明确的账单文件。映射表 `财报` sheet 的第 1 行需要 `店铺编码`、`店铺名称`；账单文件去掉扩展名后与映射中的店铺名称匹配。这是原程序已有规则，不由适配器重新推断。

业务参数示例（合成数据）：

```json
{
  "period": "2026-07",
  "mapping_file": "shops.xlsx",
  "bill_files": ["SYNTHETIC_SHOP_A.xlsx", "SYNTHETIC_SHOP_B.xlsx"]
}
```

只允许以上三个参数，最多 20 个账单。文件名不是任意机器路径；适配器从执行器给出的 `input_manifest` 精确匹配文件，并检查名称、扩展名、唯一性及 SHA256。清单中的文件必须全部属于本次声明，不扫描“最新目录”，不改变原始输入。输出位置由执行器上下文指定，非空目录拒绝复用。

原始账单必须包含 `订单明细`、`推广明细`、`评价有礼`、`资金流水` 四个 sheet；订单/推广表头位于第 1 行，评价/资金表头位于第 5 行。具体列定义来自当前原脚本；测试合成文件按这些真实格式生成。

## 离线安全边界与成功含义

报表操作显式传递账期、映射文件和输出目录。预检操作仅生成内部离线配置：API 地址固定不可用的本机端口，key/secret/api_id 均为明确的占位标识；目标表元数据从原脚本的 `TARGET_SPECS` 常量读取。**不读取任何真实仓库配置，不验证目标接口或凭据。**

原脚本不接收 `--execute`。子启动器在原代码执行前注册 Python 审计钩子，阻止 socket 和再次启动子进程，降低误进入联网路径的风险。它不是抵抗恶意代码的安全沙箱；依然只接受已审核的可信源程序和平台发布版本。

| 操作 | 返回成功的含义 | 不代表 |
| --- | --- | --- |
| check | 原报表脚本退出 0，且报表数与账单数一致 | 截图、ERP 等外部金额已经核对，或数据已上传 |
| preflight | 原程序结构预检退出 0，当前 run 的 manifest 为 execute=false | 全部金额/日期逐字段有效，实际目标配置正确，或服务端入库成功 |

失败保持原程序非零退出码并输出标准失败结果；即使原程序生成了诊断文件，也不会把它当成功。报表和 manifest 作为受控产物登记。取消前检查取消标志，运行时停止并等待旧进程；外层执行器仍负责整棵进程树及强制停止验证。

## 已验证的原有限制

`pdd_billing_warehouse_load.py` 的主流程以 `store_rows=False` 调用 `prepare_payload`，该分支主要检查 sheet、表头、映射及行数，不调用金额、日期字段的转换。合成订单金额改成 `INVALID_AMOUNT` 或成交日期改成 `INVALID_DATE` 后：

- 原结构预检退出 0；适配摘要明确它未验证金额/日期逐字段有效性。
- 同一数据的原报表程序退出 2；适配结果为 failed。

这不是适配器修复过的业务逻辑。正式上传前仍需业务方决定完整校验与成功判据；不能因为本包的 preflight 成功就自动放行上传。原程序校验报告详细程度及实际服务端行为尚未作为此工作包的功能保证。

保留所有表头但没有明细时，原报表与预检同样允许成功，分别产生零合计报表或零行 manifest。测试记录该真实行为；业务上是否允许零行数据需另外确认，适配器不擅自把它改成错误，也不把零行当作完整交付的证明。
